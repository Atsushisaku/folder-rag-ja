# チャンクとは（具体例つき）

[構造の解説](ARCHITECTURE.md) の「3.3 チャンクに分ける」を、実例を使って詳しく説明します。
例はすべて、このアプリのコード（[rag_chat/loaders.py](../rag_chat/loaders.py)・[rag_chat/chunking.py](../rag_chat/chunking.py)）で `sample_data/` を実際に処理した結果です。

---

## 1. チャンクとは

**チャンク**は、文書を検索しやすい大きさに切り分けた「ひとかたまり」の文章です。このアプリでは、チャンクが次の 3 つを兼ねています。

1. **検索の単位**：質問に近いものを、ファイル単位ではなくチャンク単位で探す
2. **LLM に渡す資料の単位**：検索で選ばれた上位 5 チャンクだけを LLM に渡す
3. **出典の単位**：「参照: 経費精算.md > 締め日と支払日」のように、どのチャンクを使ったかを示す

本に例えると、「この本に書いてある」ではなく「この段落に書いてある」と付箋を貼っておくイメージです。

## 2. なぜ切り分けるのか

ファイルをまるごと 1 つの単位にすると、次の問題が起きます。

- **意味がぼやける**：埋め込み（意味のベクトル化）は、1 つの文章を 1 つのベクトルに圧縮します。経費マニュアル全体を 1 ベクトルにすると、「対象経費」「申請方法」「締め日」「紛失時」の意味が混ざり、「レシートをなくした」という質問とのピントが合いにくくなります。
- **LLM の負担が増える**：関係ない部分まで渡すと、小さいモデルは読み違えやすく、CPU では読むだけで時間もかかります。
- **出典が粗くなる**：「経費精算.md のどこか」としか示せません。

## 3. 実例：sample_data の経費精算.md

### 手順 1：見出しで区切る（セクション）

| セクション（location） | 文字数 |
|---|---|
| 経費精算マニュアル > 対象となる経費 | 68 |
| 経費精算マニュアル > 申請方法 | 105 |
| 経費精算マニュアル > 締め日と支払日 | 78 |
| 経費精算マニュアル > 領収書を紛失した場合 | 50 |

### 手順 2：500 文字を超えるセクションだけをさらに切る

どのセクションも 500 文字未満なので、**4 セクションがそのまま 4 チャンク**になります。たとえば 3 つ目のチャンクの本文はこれです。

```
毎月 20 日締め、翌月 10 日に給与口座へ振り込まれます。
締め日を過ぎた申請は翌月分として扱われます。3 か月以上前の経費は原則として精算できません。
```

### 手順 3：埋め込むときに見出しを付ける

```
経費精算 / 経費精算マニュアル > 締め日と支払日      ← ファイル名と見出しを先頭に足す
毎月 20 日締め、翌月 10 日に給与口座へ振り込まれます。
締め日を過ぎた申請は翌月分として扱われます。3 か月以上前の経費は原則として精算できません。
```

見出しを足すのは、本文に無い語（ここでは「支払日」や「経費精算」）でも検索にかかるようにするためです（[`_with_header()`](../rag_chat/index.py#L301)）。

## 4. 大きさによって何が変わるか

### 小さすぎる場合

試しに上限を 60 文字（重なり 20 文字）にして、同じ「締め日と支払日」を切ると、こうなります。

```
チャンク1 (60文字): 毎月 20 日締め、翌月 10 日に給与口座へ振り込まれます。締め日を過ぎた申請は翌月分として扱われます。3 か月以上前
チャンク2 (37文字): は翌月分として扱われます。3 か月以上前の経費は原則として精算できません。
```

- 「3 か月以上前」で文が途中で切れています。チャンク 2 は「は翌月分…」という文の途中から始まり、単独では意味が取りにくくなります。
- 申請方法のような手順の場合、「3. 領収書の写真をアップロード」だけのチャンクができると、何のシステムの手順なのか（「ケイヒくん」）が分からなくなります。

### 大きすぎる場合

上限を 5000 文字にすると、経費精算.md はまるごと 1 チャンクになります。「レシートをなくした」と聞いても、4 つの話題すべてを含む塊が丸ごと LLM に渡ります。

答え自体は含まれていますが、検索のピントが甘くなり、LLM が関係ない部分（申請方法など）を答えてしまう危険が増えます。
実際、開発中にも「レシートをなくした」という質問に申請方法を答えてしまったことがあります。これは検索の順位が原因でしたが、渡す資料に雑音が多いと同じ失敗が起きやすくなります。

### まとめ

| | 小さいチャンク | 大きいチャンク |
|---|---|---|
| 検索のピント | 合いやすい | ぼやけやすい |
| 文脈 | 失われやすい（文や手順が途中で切れる） | 残りやすい |
| LLM への雑音 | 少ない | 多い |
| チャンクの数 | 多い（索引が大きくなり、作るのに時間がかかる） | 少ない |

このアプリの既定は 500 文字です。マニュアルの 1 つの項目（見出し 1 つ分）がだいたい収まる大きさを目安にしています。

## 5. 「重なり（overlap）」の役割

上の 60 文字の例で、「**は翌月分として扱われます。3 か月以上前**」が両方のチャンクに入っているのが重なりです（このアプリの既定は 80 文字）。

切れ目にかかった文を両側に残すことで、前後の文脈が失われにくくなります。その代わり、同じ文章が 2 回保存されるので、索引は少し大きくなります。

## 6. このアプリの区切り方

[`split_text()`](../rag_chat/chunking.py#L8) は、意味のまとまりを優先して、どうしても無理なときだけ機械的に切ります。

1. **見出し**（Markdown・Word）または**ページ**（PDF）で区切る
2. 500 文字を超えたら、**段落（空行）**の切れ目で区切る
3. 1 段落だけで 500 文字を超えたら、**文字数**で区切り、前のチャンクと 80 文字重ねる

## 7. 実データで気をつけたい点

- **PDF はページで区切られます。** OneNote から書き出した PDF では、1 つの手順が 2 ページにまたがると別々のチャンクになり、見出しの情報（「申請方法」など）も付きません。location は `p.3` のようなページ番号になります。
- **PDF から取り出した文字には空行が少ないことが多い**ので、段落での区切りが効かず、文字数で切られやすくなります。上の 60 文字の例のように、文の途中で切れることが増えます。
- そのため、OneNote の場合は **Word 形式で書き出す方が、見出しを生かせて有利な可能性があります**。ただし**未検証**なので、同じページを両方の形式で書き出して比べてみる価値があります。

## 8. 自分で確かめるには

`config.toml`（`config.example.toml` をコピーして作る）で `chunk_size` を 200 や 1000 に変え、索引を作り直してから次を比べます。チャンクの大きさを変えると、索引は自動で作り直されます。

```
uv run python -m rag_chat index sample_data
uv run python -m rag_chat ask sample_data "レシートをなくした" --no-llm
```

上位 5 件の顔ぶれと、`index` の出力に出る「チャンク」の数がどう変わるかに注目してください。
